# 《루루 인 비트》 화면·UI·이미지 통합 디자인 설계서
**제작 기준 v5 — 2026-11-23 | Unity 2022.3 / PC 16:9 / 마우스 전용**

> 이 문서는 “어떤 이미지를 몇 장 만들까?”보다 먼저 **게임이 플레이어에게 어떻게 보이고, 어디에서 무엇을 읽고, 어떤 버튼을 누르게 할 것인지**를 결정한다. 아래 수치는 **설계 좌표**이며, GitHub 씬에서 확인한 현재 좌표와 다른 것은 **수정 대상**으로 명시했다. 그림 제작/Unity 연결이 끝났다는 뜻이 아니다.

### 함께 확인하는 도면과 작업표
- **[타이틀·곡 선택·플레이·튜토리얼·결과·설정의 6화면 배치도](UI_SCREEN_BLUEPRINT_20261123.svg)**: *아트 완성 이미지가 아니라 화면 구성 도면*이다. 루루/피노 표시 영역에는 실제 업로드한 원본 이미지를 나중에 배치한다.
- **[개별 이미지 36개 슬롯 제작표(CSV)](IMAGE_ASSET_TASKS_20261123.csv)**: 파일별 역할·원본 크기·투명도·연결 위치·검수. 36개를 모두 새로 그리라는 의미가 아니다.
- **[저장소 기존 PNG 85개 조사 기록](IMAGE_ASSET_INVENTORY_20261122.md)**: 사용 가능 여부가 아니라 보유·연결 여부 기록.

## 1. 게임의 디자인 정체성을 먼저 결정한다

### 1.1. 게임이 줘야 할 첫인상

**“루루가 좋아할 것 같은, 팝하고 개성적인 일본 애니메이션풍 PC 리듬게임.”**

이것은 **게임기 모양의 기계 UI**가 아니다. 루루가 게임을 좋아한다는 설정은 *가상의 플라스틱 콘솔을 화면에 둘러 붙이는 장식*이 아니라, **버튼을 누르는 탄력, 화면이 전환되는 박자, 선택된 콘텐츠가 툭 튀어나오는 시각적 리듬**에서 느껴져야 한다.

- **메뉴에서는** 루루의 캐릭터 실루엣과 재킷이 주인공이다.
- **플레이에서는** 정확히 입력해야 할 마우스 노트, 피노, 탄막이 주인공이다. 모든 화면에 크고 비슷한 패널이 깔리면 실패다.
- **결과에서는** 100만 점 체계의 점수와 랭크가 가장 크게 보이며, 피노의 성공·실패 표정이 감정을 더한다.
- **설정에서는** 재미있는 그래픽보다 실제 수치와 버튼의 위치가 명확해야 한다. “팝함”은 탭 선택 애니메이션에만 얹는다.

### 1.2. 독특함을 만드는 조형 규칙 딱 세 가지

| 이름 | 화면에서의 모양 | 사용하는 곳 | 남용 금지 |
|---|---|---|---|
| **BEAT CUT** | 사각형 가장자리 **한 군데만 12~22px 잘린 사선** | 선택된 곡 행, 버튼의 한쪽 끝, 결과 랭크의 강조 | 프레임 네 귀퉁이·모든 작은 UI에 반복 금지 |
| **TWO-TONE CEL** | 매끈한 1단 밝은 면+1단 짙은 면, 가느다란 어두운 외곽선 | 패널, 버튼, 게이지, 재킷의 그래픽 기본 | 광택/글로우/3D 볼륨/메탈 금지 |
| **SHORT POP** | 입력 순간 **1회만** 1.03~1.08배 커졌다 바로 복귀, 혹은 8~16px 짧게 이동 | 곡 선택, 버튼 확인, PERFECT, 랭크 등장 | 1초 내내 흔들기/무한 박동/화면 전체 반짝임 금지 |

피노 날개나 루루 머리의 삼각·리본 덩어리는 **사선 형태를 한 번 차용할 근거**다. 캐릭터의 귀·날개·슬리퍼를 UI 아이콘으로 반복 도배하는 지시가 아니다.

### 1.3. 색은 캐릭터 사진에서 출발한다

사용자가 제공한 루루·피노 원본 두 장의 보라 영역을 실제로 추출·비교한 **작업용 참고색**이다. 일러스트 최종 픽셀과 별도 테스트 후 조정한다.

| 역할 | 기준 HEX | 어디에 쓰나 |
|---|---|---|
| 선/콘텐츠 대비 | **#20163C** | 테두리, 밝은 버튼 위의 글씨, 어두운 강조 |
| 진한 면 | **#352953** | 메뉴 백그라운드, 위험 상황 뒤쪽 |
| 기본 보라 | **#56427C** | 카드 선택 영역, 버튼 강조 |
| 또렷한 중간 보라 | **#A17ADC** | 선택/랭크/리듬 포인트 |
| 피노 연라벤더 | **#BEAAE3** | 클릭 가능한 밝은 패널 |
| 흰색에 가까운 면 | **#F6F0FC** | 본문 콘텐츠 면/여백 |
| 부가 포인트 | **#E9A7D5** | 1곳의 작은 포인트, 위기나 고랭크의 색 변화 |

**화면 비율:** 밝은 면 약 45%, 어두운 면 약 35%, 선명한 포인트 20% *이하*를 출발점으로 하되 **플레이 화면은 더 어둡고 낮은 대비의 배경**을 쓴다. “모든 버튼이 보라색”이 아니라 흰 면과 자주 면을 교차 사용한다.

**선:** 1920×1080 Unity 표시 기준 대략 2~4px로 읽히는 선. 두꺼운 6~10px 만화 외곽선과 복잡한 3중 프레임 금지. **비율:** 캐릭터 원본 외형과 명암을 최우선, UI를 캐릭터에 맞춘다.

### 1.4. 참고 게임에서 실제로 가져올 것은 디자인 원리뿐

- **Hi-Fi RUSH:** UI가 입력/음악에 반응하는 *동작의 역할*만 참고. 강렬한 만화 효과·금속·네온 스타일은 가져오지 않는다. 리듬 게임의 반응이 배경만 번쩍이는 것으로 보이지 않게 한다. 참고: https://www.digitaltrends.com/gaming/hi-fi-rush-john-johanas-interview/
- **UNBEATABLE:** 텍스트 크기·큰 숫자로 플레이 결과를 강하게 보여 주는 **타이포그래피의 계층**만 참고. 글리치/번짐/노이즈·화면 분할 스타일은 복제하지 않는다. 참고: https://store.steampowered.com/app/1290490/UNBEATABLE_white_label/
- **Rhythm Doctor:** **게임 플레이를 읽기 쉬운 상태로 두고** 플레이 자체를 시각적 서사의 중심에 둔다는 원리를 참고. 픽셀아트나 심전도 모양은 사용하지 않는다. 참고: https://store.steampowered.com/app/774181/Rhythm_Doctor/

**참고자료는 복제용 UI 시트가 아니다.** 《루루 인 비트》의 색/인물/선 질감은 사용자 루루·피노 이미지에서 결정한다.

## 2. 실제 게임의 화면 흐름 (스토리·기능의 전체 경험)

\`\`\`text
타이틀
 ├─ 설정 / 크레딧 / 종료 확인 ──> 타이틀 복귀
 └─ 게임 시작
     ├─ 첫 진입 ──> 짧은 프롤로그 ──> 튜토리얼 6단계 ──> 완료 대화
     │                                              └──> 곡 선택
     └─ 튜토리얼 완료 기록 있음 ─────────────────────────> 곡 선택
                                                       ├─ 튜토리얼 다시하기
                                                       └─ 곡 선택(현재 6곡)
                                                           └─ 플레이(MOUSE)
                                                               ├─ ESC 일시정지 / 재개
                                                               └─ 결과 CLEAR/FAILED
                                                                   ├─ 다시하기
                                                                   └─ 곡 선택
\`\`\`

**현재 있는 것:** TitleScene, SongSelectScene, Mouse, Tutorial과 첫 진입 튜토리얼 코드, 곡 선택/결과 시스템. **아직 없는 것:** 별도의 Story 씬·본편 스토리 에피소드. 스토리 그림을 모두 만든 것처럼 주장하지 않는다.

**스토리 도입 제안의 범위:** “게임을 좋아하는 루루 → 피노가 게임의 이상을 알려 줌 → 조작을 익히며 문제를 확인 → 여섯 곡 자유 플레이”까지만 현재 튜토리얼 대화·게임 기능과 이어진다. 이후 곡마다 새로운 사건/보스 대사/엔딩을 즉흥적으로 확정하여 이미지를 양산하지 않는다.

## 3. 화면별 설계 — 실제 1920×1080 기준

아래 **x,y는 화면 왼쪽 위가 (0,0)** 인 설계 좌표다. 실제 Unity에서는 RectTransform 앵커·피벗으로 환산한다. 숫자는 화면을 어떻게 쓰자는 결정이고, 현재 씬이 완성됐다는 주장이 아니다.

### 3-1. 타이틀 — *루루와 게임의 분위기*

| 영역 | 좌표 / 치수(기준안) | 내용·그림 배치 |
|---|---|---|
| 전체 | x0~1920, y0~1080 | 사용자 원본 그림체와 맞는 **한 장의 조용한 배경**. 짙은 보라·연보라의 낮은 대비 |
| 루루 전신 | x100~1050, y60~1040 | **업로드된 루루 원본 누끼 이미지**. 긴 머리와 발끝을 자르지 않는다. 화면을 가득 채우되 과도한 얼굴 확대 금지 |
| 로고 | x1190~1840, y100~350 | 기존 로고 PNG 사용. **우측 상단 비움**이라는 이전 확정 요청을 지킨다 |
| 메뉴 3버튼 | x1260~1800, y430~790 | 시작/설정/종료. 한줄 450~510×82~96, 버튼 간 18~28px 여백 |
| 제작 정보 | x1220~1820, y975~1030 | 작은 안내·버전/고지. 24px 내외의 읽히는 글씨, 큰 장식 프레임 필요 없음 |

**구성 스케치**

\`\`\`text
┌────────────────────────────────────────────────────────┐
│  조용한 게임 세계             ┌── 기존 LOGO ─────────┐ │
│                              └──────────────────────┘ │
│     루루 원본 전신                 [ 게임 시작 ]         │
│     (독립 PNG 레이어)              [ 설정 ]             │
│                                    [ 종료 ]             │
│                   하단 작은 고지 / 버전                 │
└────────────────────────────────────────────────────────┘
\`\`\`

- **장식 문법:** 3버튼 중 현재 마우스가 가리키는 버튼만 라벤더 면이 팝업되고 한쪽 모서리 컷이 선명해진다. 로고 뒤에 보라색 프레임을 또 씌우지 않는다.
- **루루 방을 배경으로 쓸 경우:** 실제로 가능한 방 구조(책상·모니터·의자·소품)여야 한다. 사용자 요청 없던 방 소품/기계를 무작위로 채우지 않는다. **배경·루루·로고·버튼·글씨는 분리**.
- **현재 씬과 차이:** TitleScene 로고가 약 700×400, 중앙 기준 x=+650에 있어 1920 폭에서 일부 가장자리와 가까움. 이 새 안전영역 안으로 배치를 조정해야 한다.

**이미지:** 기존 로고, \`Lulu_Cutout.png\`(원본 분리), \`Story_LuluRoom.png\` 또는 심플 BG(아트 검토 후 택1), 공용 버튼.

### 3-2. 곡 선택 — *왼쪽 6곡, 오른쪽 재킷 중심*

| 영역 | 기준 설계 | 내용 |
|---|---|---|
| 상단 제목 | x78~1838, y50~145 | SONG SELECT/현재 곡 수와 선택 도움말; 긴 화려한 타이틀 프레임 불필요 |
| **왼쪽 목록** | x80~1070, y200~895 | 곡 6줄. 각각 높이 94~100, 줄 간격 10~14. **선택 줄 하나만** 밝게 나와 앞에 있는 느낌 |
| **오른쪽 재킷** | x1220~1680, y215~675 | **정사각형 460×460**. 재킷 그림에 가짜 메뉴/프레임/타이틀 그리지 않음 |
| 오른쪽 정보 | x1130~1840, y705~900 | 곡명, 난이도, 최고점수, 미리듣기. 난이도 선택은 작은 좌우 버튼/색 변경 |
| 플레이 | x1480~1840, y920~1000 | 분명한 **PLAY** 하나. 좌측 목록과 일관된 BEAT CUT 형태 |
| 뒤로 | x75~300, y947~1020 | 작은 뒤로 버튼. 튜토리얼 재진입은 별도 눈에 띄는 선택 가능 메뉴 |

**현재 씬 근거:** SongSelectScene TrackListPanel이 화면 가로 4.1~57.0%, SelectedTrackPanel이 58.4~96.0%다. 기존 좌우 구조는 **유지한다**. 새 그림 때문에 양쪽을 뒤집거나 모바일형 세로 카드 목록으로 바꾸지 않는다.

**모션:** 선택 줄 x방향으로 8~14px 이동+재킷 120~180ms 스케일 0.97→1.0, 곡명은 교체. 선택하지 않은 다섯 줄은 고정. **곡 재킷을 누르고 있는 동안 전체 화면이 박자마다 반짝이는 연출 금지**.

**이미지:** 곡별 재킷 6개의 실제 슬롯(기존 2개 품질 검수 후 부족한 만큼만 제작), 공용 버튼/탭, 목록의 배경은 Unity UI 색 면으로 가능한 한 코드 조립. 한 곡당 새 UI 프레임 6개를 그리지 않는다.

### 3-3. 플레이 — *정보보다 노트와 피노가 먼저 보이도록*

**최우선 규칙:** 기존 Mouse/PlayArea는 거의 전체 화면이다(약 1836×977). **이미지 만들기 전에 안전한 HUD 공간을 실제로 확보**해야 한다. 노트 스폰 위치가 정규화 좌표를 쓰므로 영역을 옮긴다면 접근/판정 좌표도 함께 점검한다.

| 피격 경고 | 피노 주위/안정화 바 순간 반응 | 1 | 큰 위험 패널이 노트를 가리지 않음 |
| PAUSE | **화면 상시 버튼 없음** | - | ESC로만 열기 |

**팝 아트는 판정과 동작에 집중.** PERFECT 때 노트 주변에 얇은 셀풍 1회 커짐/사라짐은 가능하지만, 전체 스크린 글로우나 노트를 못 보게 하는 화려한 형상은 실패. **기존 마우스 노트 이미지는 만들지 않는다**.

**배경:** 먼저 중앙 시인성 검증. 곡별 그림 6장 슬롯은 있지만, 데모에서 **공통 1장으로 잘 보인다면 무조건 다른 5장을 요구하지 않는다**. 곡별 BG를 쓰는 경우에도 화면 한가운데에 장식/원형 패턴 없음.

### 3-4. 튜토리얼 — *스토리·학습·실습을 세 가지 상태로 분리*

**현재 구현 확인:** Tutorial.unity가 Mouse를 기반으로 하며, \`MouseTutorialController\`에는 프롤로그 대화와 6챕터가 있다. 그러나 \`TutorialGuide\` 현재 위치가 x=70~97.5%, y=20~43%로 **실제 노트 공간과 겹친다**. 이것을 새 패널 그림만 덧씌워서 해결하면 실패다.

| 상태 | 실제 보이는 화면 | 버튼/입력 | 이미지 |
|---|---|---|---|
| **A. 프롤로그** | 배경 위에 루루와 피노 초상(필요한 화자만) + 화면 하단 가로 대화창 | 다음/연습 시작, 마우스 | 두 원본 컷아웃 + 공용 대화 패널/버튼 |
| **B. 단계 안내·체크포인트(시간 정지)** | 게임 일시정지/어두운 레이어/피노 초상+그 단계 제목·짧은 대사 | 계속 | 공용 대화 패널, 이동·좌·우·휠 아이콘 |
| **C. 실제 실습** | 위의 큰 대화창·초상 숨김. **상단 1줄 48~56px 안내만**. 노트·피노·탄막은 전부 표시 | 마우스 좌/우/휠/이동 | 상단 작은 텍스트, 필요한 경우 작은 단계 아이콘 |
| **D. 완료 대화** | 결과가 아닌 짧은 대사 화면, 곡 선택으로 이동/재연습 | 버튼 2개 | 공용 패널, 루루/피노 초상 |

**6챕터 실제 진행 순서:** 이동 → 왼쪽 클릭 → 오른쪽 클릭 → 휠 → 탄막 회피 → 리듬·회피 동시. 새로운 노트/탄막 스프라이트를 튜토리얼용으로 만들지 않는다.

**화면 배치:** 하단 대화창 x250~1670, y750~1030. 캐릭터는 한쪽 x60~430 또는 x1450~1850에 분리 레이어. **대화 중에만 게임이 정지**해 판정 시야를 덮는 것을 허용. 실습 중에는 위의 큰 그림을 숨긴다.

**참고 구조:** 이야기 도입→체험→짧은 확인→다음 단계→마지막 실전→완료. 조작 설명을 여섯 장의 벽 같은 도움말로 만들지 않는다.

### 3-5. 결과 — *게임이 끝난 순간 시각적으로 가장 크게 보이는 화면*

**핵심:** 컴퓨터 설정 대화창처럼 큰 직사각형에 모든 숫자를 나열하는 디자인 금지. 결과는 **스테이지의 결말**이다.

| 좌측 캐릭터 | x100~650, y185~970 | 기존 \`피노_Clear.png\` 또는 \`피노_False.png\`; 실제 비율 유지 |
| 결과 헤드라인 | x730~1740, y110~260 | **CLEAR / FAILED** 매우 크게 TMP. 진보라·핑크의 **한 번만** 사선 등장 |

| 랭크 | x1450~1790, y300~535 | SS/S/A/B/C를 거대한 글자로. 배지 그림보다 **랭크 글자 자체**를 주인공으로 |

**이미지:** 기존 피노 성공/실패 애니메이션, 공용 Button, 점수 통계용 공용 Panel(필요 부분만). **전체 결과를 하나의 PNG로 그리지 않는다.** 런타임 \`ResultPanel_Runtime\`은 교체/재구성해야 하는 코드 작업이다.

| 영역 | 기준 좌표 | 내용 |

**기존 UI에서 확인한 문제:** TitleScene에는 구형 \`Lane1KeyRow\` 등 4레인 키보드 설정이 남아 있다. **설정 그림만 새로 그려서는 해결되지 않는다.** 마우스 조작 안내·실제 옵션으로 정리해야 한다. 사용자 요청 없는 단축키를 설정에서 새로 만들어 내지 않는다.

## 4. 스토리 아트와 6곡 음악 아트의 제작 원칙

### 4-1. 스토리는 먼저 ‘장면’을 정하고 그림을 그린다

**현재 GitHub에는 별도 본편 Story 씬이 없다.** 이미 확정된 것처럼 본편 컷신 20장, 감정 표정 30종을 주문하지 않는다.

**지금 필요한 최소 장면 설계:**

| 컷 | 장소·동작 | 시각 자산 | 코드/기획 작업 |
|---|---|---|---|
| 01 | 루루가 게임을 시작하는 도입 | 루루 **사용자 원본** + 실제 타이틀 배경 재사용 | 새 스토리 버튼 없이 최초 튜토리얼 연결 |
| 02 | 피노가 이상을 알려 주는 대화 | 루루/피노 원본 초상 + 공용 패널 | 기존 프롤로그 대사 단계의 연출 및 텍스트 검수 |
| 03 | 이상이 발생한 게임 공간으로 진입 | 게임 속 이상 공간 배경 1장 **또는 현재 게임 배경 재사용** | 씬 전환/단계 진행 |
| 04 | 조작을 배운 뒤 곡 선택으로 복귀 | 루루/피노 초상 + 공용 패널 | 완료 플래그/6곡 자유 플레이 |

**방 배경 \`Story_LuluRoom.png\`을 반드시 만들어야 한다는 이전 지시는 철회한다.** 사용자가 이미 타이틀 방 구조를 여러 번 지적했으므로, 실제 타이틀 화면에서 **루루를 배치한 다음 필요한 공간만** 배경으로 설계한다. 방을 만들 경우 원근이 맞는 책상·의자·모니터·벽만 갖춘 하나의 공간으로 제한. 방이 필요 없으면 추상적 *팝 애니* 단색 무대 1장으로 구성한다.

### 4-2. 곡 재킷 6장은 ‘곡을 듣고’ 디자인한다

현재 저장소에는 여섯 음원과 6개 차트 관련 파일이 있다. **곡 제목만 보고 무작위 원·리본·속도선으로 6개 재킷을 만드는 계획은 폐기한다.** 그것은 실제 음악에 맞춘 앨범 아트가 아니다.

**매 곡에 대해 제작 전에 작성해야 할 미니 브리프 6항목**
1. 곡 제목 / 길이 / 실제 음원 도입과 후반의 성격
2. 주요 리듬 악센트 / 분위기 변화 / 음악적 모티프
3. **1개 중심 대상**: 캐릭터·장소·소품·기하 그래픽 중 곡에 실제로 맞는 것
4. 1차/2차 대비색과 주요 실루엣
5. 1024×1024 큰 그림과 160×160 작은 표시에서 각각 읽히는지
6. 다른 다섯 재킷과 **형태·색·중심 소재**가 명확히 구별되는지

| 곡 | 연결 대상 | 재킷 제작 결정 |
|---|---|---|
| BOOTBEAT | BOOTBEAT_MOUSE_LV6 songSelectJacket | 현재 재킷 후보 확인 → 음원 도입의 특징을 핵심 비주얼로 |
| Oddbeat Shuffle | ArcadeGroove_MOUSE | 셔플 리듬이 실제로 청감상 두드러지는지 확인한 뒤 비주얼 선택 |
| Full-Band Hit | FullBandHit_MOUSE | 실제 악기 편성/강한 타격감 확인 후 소재 결정 |
| 瞬奏 -SHUNSOU- | MabatakiNoSenritsu_MOUSE | 음악 속 속도/긴장 변화로 구도 결정 |
| Cotton Pulse | RhythmGameTheme_MOUSE | 부드러움/박동 인상이 실제 음악과 맞는지 확인 |
| Pop'n Dash | popn_dash | 실제 곡 성격과 기존 재킷·배경 자산을 비교 |

**지금 판정:** \`Assets/Image2/SongJaket/\` 기존 2장을 실제 확인하지 못했으므로 모두 ‘검수 필요’. 재킷의 일러스트와 UI 테두리는 합치지 않고, 제목/아티스트/난이도는 TMP.

### 4-3. 곡별 플레이 배경은 ‘보이는가’로 결정한다

곡마다 \`backgroundImage\` 슬롯이 있지만 **모든 곡에 새 1920×1080 그림이 필수라는 뜻은 아니다**. 현재 Pop'n Dash는 기존 SongIllust 참조가 있고, 다른 곡의 배경 슬롯은 비어 있다.

**기본 데모:** 게임의 공통 낮은 대비 플레이 배경을 먼저 고정하고 **6곡 전체의 마우스 노트·탄막·피노를 실제 플레이 검수**. 곡마다 감정 변화가 부족한 경우에만 배경 자산을 추가. 새 곡 BG를 만들면 중앙 **가로 70%, 높이 70%는 큰 명암 변화/탄막 같은 점/원형 링 없음**. 모티프는 양쪽 가장자리 위주. 재킷을 확대한 배경 금지.

**왜 패널을 1개만 만들면서 화면은 다르게 보이나?** 타이틀에는 큰 패널 자체를 쓰지 않고, 곡 선택은 카드 행/재킷/선택 상태가 주인공, 플레이는 상단 HUD만, 결과는 **큰 글씨가 주인공**이다. 패널 이미지가 모든 화면의 디자인을 대신하면 실패다.

| **곡별 재킷 6슬롯** | 1024×1024, 1:1 | 각 곡 음원 분석 후 독립 아트 제작. **기존 2개는 검수 필요** |
| 타이틀/프롤로그 배경 | 1920×1080 | 실제 배치에 필요한 수량만. 인물·로고·버튼을 배경에 굽지 않음 |
| 곡별 배경(조건부) | 1920×1080 | 이미 있는 공통/Pop'n Dash BG 검수 후 필요할 때만. 중앙 플레이 가독성 최우선 |
| 기존 피노 idle/Hit/Clear/False | 기존 파일 유지 | 게임플레이와 결과. 애니메이션 프레임/스프라이트 GUID 변경 금지 |
| 기존 Enemy01/바이러스 | 기존 파일 유지 | 현재 코드를 우선 사용. 무단 새 적·탄막 그림 생성 금지 |
| **새 마우스 노트 PNG** | **0개** | 기존 코드 생성 노트 원형/링/휠 경로 그대로 |

### 5-4. 각 PNG의 ‘진짜 Unity 사용 가능’ 기준

1. 32bit RGBA 실제 투명 알파. **흰 배경·체크무늬·검은 박스를 합성한 가짜 투명 PNG는 불합격**.
2. 그림 내부에 글씨, 퍼센트, 버튼 상태, 선택 화살표, 캐릭터가 달려 있지 않음. 기능별 레이어 분리.
3. 9-slice는 모서리 4곳을 유지하고 중앙만 늘어난다. **640×256→1250×300 / 450×240 / 1100×650** 실측.
4. 버튼은 기본 이미지 **한 장**만 사용하고 Color Tint/Scale로 상태 구현. 눌림/호버 전용 PNG 중복 양산 금지.
5. 게이지는 프레임, 빈 바닥, 채움 **정확히 3개 Sprite**와 TMP 수치 1개. **100·60·20·0%** 렌더링 검사.
6. Mouse/Tutorial의 NoteLayer/피노 클릭 감지 범위 위에 장식 Image를 놓는 경우 **raycastTarget=false**. 게임 입력 방해 금지.
7. 파일이 **실제 Unity GameObject/코드 연결 없이 저장소에만 있으면 완료가 아니다.**

## 6. 화면별 동작 연출 사양 (그림이 살아나는 조건)

| 상황 | 권장 동작 | 그림이 필요한가 | 실패 기준 |
|---|---|---|---|
| 타이틀 버튼 hover | 100~140ms, scale 1→1.04 | 공용 버튼 1개 | 시선이 루루 얼굴보다 계속 흔들리는 효과 |
| 곡 선택 | 130~180ms, 선택 행 x+12px, 재킷 0.97→1 | 재킷 1개 + 기존 UI | 모든 행이 동시에 움직임 |
| 곡 미리듣기 | 오디오 크로스페이드와 표시 상태 변화 | 새 그림 불필요 | 이미지 스펙트럼이 텍스트/재킷을 덮음 |
| PERFECT | 판정 텍스트 100~160ms 탄성 후 200~300ms 내 사라짐 | 코드/TMP 우선 | 가짜 노트가 겹쳐 보임 |
| 콤보 변화 | scale 1→1.08→1 / 약 150ms | 기존 TMP 우선 | 노트 주변 화면에 계속 큰 숫자 고정 |
| 피노 피격 | 피노/안정화 80~150ms 상태 표시 | 기존 Hit/게이지 | 화면 전체 레이저·진동으로 다음 노트 못 읽음 |
| 안정화 감소 | fillAmount 값 변경 / 위기 시 색 변환 | Frame/Track/Fill 3개 | 임시 게이지와 중복 표시 |
| 튜토리얼 체크포인트 | 시간 정지→대화창→마우스 클릭 해제 후 재개 | 패널/캐릭터/아이콘 | 계속 클릭이 MISS로 판정되거나 진행 중 노트 가림 |
| 결과 CLEAR | 헤드라인 200ms→점수 400ms→랭크 180ms | TMP + 피노 결과 이미지 | 강제 연출이 너무 길어 재시도가 늦어짐 |
| ESC 일시정지 | 배경 어둡게, 공용 패널 하나 | 패널/버튼 | 상시 PAUSE 버튼/노트 계속 흐름 |

위 시간들은 **최종 튜닝 전의 구현 시작값**이다. 과한 광택이나 추가 장식 PNG로 대신하지 않는다.

## 7. 제작·개발을 병행하는 확정 작업 순서

**1단계 — 설계 도면과 원본 확보**
- 6화면 도면대로 실제 Unity의 화면 좌표·아트 레이어 목록을 확정.
- 사용자가 준 **루루/피노 원본**을 배경 제거한 별도 PNG로 준비. 인물 재생성 없음.
- 실제 TitleScene / SongSelectScene / Mouse / Tutorial **현재 Game View**와 새 배치를 비교.

**2단계 — 플레이에서 가장 중요한 최소 UI**
- \`Stability_Frame/Track/Fill\`을 각 1개 제작/분리.
- PlayArea와 충돌 없는 상단 72px 정보 띠를 확보하고 안정화 수치·Combo·Score를 배치.
- 기존 노트·탄막은 그대로 유지하면서 실제 고밀도 채보에서 가독성 확인. **여기까지가 게임플레이 HUD의 첫 합격 조건**.

**3단계 — 선택·설정·대화 컴포넌트**
- 공용 Panel / Button / Tab을 만들고 **실제 세 가지 크기 이상에서** 사용.
- 설정 Slider(3분리), Toggle(2분리), 필요 시 Scrollbar(2분리)의 **기존 파일 사용 가능 여부**를 먼저 검사.
- 튜토리얼 설명은 **대화 중 큰 패널 / 실습 중 1줄 안내**로 정리.

**4단계 — 화면 고유 콘텐츠**
- 기존 두 장 재킷 실제 확인 + 여섯 곡 음원 특징 확인→곡별 1:1 커버 이미지 완성.
- 사용자 루루 원본/로고 위치를 맞춘 타이틀 이미지, 필요하다면 프롤로그 배경.
- 6곡에서 실제 플레이 배경이 부족한 경우에만 곡별 배경 추가.

**5단계 — 마무리 결과 및 흐름 검증**
- ResultPanel_Runtime을 큰 점수/랭크 위주로 재구성, 기존 피노 Clear/False 이미지를 화면에 실제 연결.
- 설정의 구형 4레인 키 기능과 버튼 라벨을 제거, 마우스 전용 설명·현재 기능으로 정리.
- 1920×1080 / 1600×900 / 1366×768에서 **타이틀→최초 튜토리얼→곡 선택→6곡 플레이→결과→재도전**, ESC/설정/튜토리얼 재진입까지 확인.

**“작업 완료”의 정의:** 이미지 개수가 많아서가 아니라, **완성된 스프라이트가 실제 Scene/ScriptableObject에 적용되고 PC에서 플레이 입력을 방해하지 않는 것.** 검증 전에는 완료 표시하지 않는다.

## 8. 현재 확정되지 않은 것과 거짓으로 채우면 안 되는 정보

- **본편 스토리의 줄거리·챕터 수·새 캐릭터·바이러스 정체:** 아직 미확정. 대사/이벤트 승인 없이 스토리 CG를 무턱대고 만들지 않는다.
- **개별 6곡의 실제 음악적 스타일과 일러스트 주제:** 음원을 듣고 분석하지 않은 상태에서 곡 제목만 보고 추측한 도형 아트를 최종안으로 단정하지 않는다.
- **기존 타이틀/설정/재킷 파일의 실제 쓸 만한 품질:** 보유·GUID 참조와 아트 품질 검수는 다른 단계. **쓸 수 없으면 기존 그림이 있다고 완료로 처리하지 않는다**.
- **실제 Unity Game View에서의 색 대비/노트 충돌:** YAML RectTransform 및 코드 읽기만으로 최종 플레이 시인성이 합격됐다고 표시하지 않는다.
- **이 문서의 픽셀 좌표/초기 모션 시간:** 실제 장면으로 검증해야 하는 제안값.
